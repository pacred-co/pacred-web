# ด่านนำเข้า (staging gate) ที่แก้ไขได้ — 4 บทเรียนจากรอบ 2026-07-25/26

> บริบท: owner สั่งให้ตารางนำเข้า MOMO "แก้ไขได้ทุกคอลัมน์ · ข้อมูลที่กรอกต้องถูกนำไปใช้จริง
> เชื่อมโยงถึงกันทั้งหมด" — ระหว่างทำเจอกับดัก 4 ตัวที่จะเจอซ้ำแน่ในงานคล้ายกัน
> (ttw staging · carrier manual · ทุกตารางที่ sync จากพาร์ทเนอร์แล้วให้คนแก้ทับ)

## 1. ตาราง staging ที่ partner-sync ทับได้ — ค่าที่คนกรอกต้องมีบ้านของตัวเอง

**อาการ:** เปิดช่องแก้ไขบนตาราง staging โดยเขียนลง `raw`/คอลัมน์ metric ตรงๆ →
ใช้ได้ตอนกด แต่ **sync รอบถัดไป (ทุก ~5 นาที) upsert ทับทั้งก้อน** → ของที่กรอกหายเงียบ
เฉพาะแถวที่ยังอยู่ใน feed window (แถวเก่าที่หลุด window ไม่โดน → บั๊ก "บางแถวหาย บางแถวอยู่"
ที่ debug ยากมาก · dims ของภูมเขียนแบบนี้มา 11 วันก่อนถูกจับได้รอบนี้).

**กติกา:** ค่าที่แอดมินกรอกบนตารางที่ partner sync ทับได้ ต้องเก็บใน**คอลัมน์ที่ sync
ไม่มีวันแตะ** (`admin_patch jsonb` — mig 0282) แล้ว **overlay ตอนอ่านทุกทาง**:
- จอ (page.tsx): `patch.X ?? synced.X`
- **ตัวนำเข้า/ตีมูลค่า (commit)**: ทับลง srcRow **ที่จุดเดียวต้นทาง** ก่อน logic อื่นทั้งหมด
  — โค้ด valuation/dedup ที่เหลือไม่ต้องรู้จัก patch เลย
- เขียน 2 ชั้นได้ (คอลัมน์เดิมด้วย = พฤติกรรมเดิมไม่สะดุด) แต่ **patch คือ SOT**

**สิ่งที่ห้ามทำ:** แก้ `momo_tracking_no` (คีย์ conflict ของ sync) — rename แล้วรอบถัดไป
MOMO ส่งเลขเดิมมา = insert แถวใหม่ = เครื่องปั๊ม dup. เลขที่ถูกต้องเก็บเป็น
`tracking_override` (mig 0281) แล้วต่อ **สาย alias** ให้ครบ: commit ใช้เลขแก้ ·
propagate remap · ตัวจับคู่บิล MOMO เพิ่มชั้น `staging_alias` (บิลมาเลขเดิม → หางานเจอ).

## 2. DB constraint = จุดบอดของ gate ทุกตัว → rollback-INSERT test + source guard

**เคสจริง:** เพิ่มฟีเจอร์แกลเลอรี → เขียน `fimages: null` แต่คอลัมน์เป็น NOT NULL
DEFAULT `'[]'` → **ทุกการนำเข้าตาย 23502 พร้อมกันทั้งหน้า** ทั้งที่ tsc/lint/build/test:unit
**เขียวหมด** — ไม่มี gate ตัวไหนรู้จัก constraint ของฐานข้อมูล. รู้ตอน owner กด.

**กติกาใหม่ (ใช้กับทุกฟีเจอร์ที่แตะ INSERT ตาราง legacy):**
1. **rollback-INSERT test** — ยิงชุดคอลัมน์จริงลง prod ใน txn แล้ว ROLLBACK เสมอ
   (`scripts/verify-momo-commit-insert-2026-07-25.ts` · 7 เคสใช้งานจริง + 1 เคส
   regression ที่**ต้องพัง** = พิสูจน์ว่าเทสไม่หลอก · ยืนยัน 0 แถวค้างทุกครั้ง)
2. **source-scan guard ลง test:unit** — สแนปช็อตรายชื่อคอลัมน์ NOT NULL จาก prod
   แล้วสแกนโค้ด INSERT ว่ามีใครเขียน null ทับ (`lib/admin/momo-commit-insert-guard.test.ts`)
   · **ต้องพิสูจน์ว่ายามจับได้จริง**: ใส่บั๊กกลับ → ต้องแดง · เอาออก → เขียว

## 3. พาร์ทเนอร์เปิดเรคคอร์ดซ้ำให้พัสดุใบเดียว (เคส 733) — กัน 3 ชั้น + หลักฐานก่อนสรุป

MOMO มี 2 เรคคอร์ดต่อพัสดุเดียวได้: ร้านประกาศเลขเต็ม (0kg ค้างตลอด) + โกดังชั่งแล้ว
คีย์เลขสั้น (มีน้ำหนัก/CG/ตู้/**รูปป้ายที่เขียนเลขเต็มเอง** = ตัวมัด). วิธีปิด:
- **UI**: แถวผีขึ้นป้าย "🔁 ซ้ำ — ใช้แถว X" + hold ออกจาก bulk (ป้ายกันคนตาไว)
- **SERVER**: commit refuse แถวที่ถูกเคลม (fail-CLOSED · ครอบ cron ด้วย — ป้ายบนจอ
  กันระบบไม่ได้) · เช็ครัศมีบน prod ก่อน ship (เจอ 1 แถวเป๊ะ = ไม่ลามงานอื่น)
- **หลัง commit**: ตัว heal เดิม (backlink) ประทับแถวผีเป็น "เข้าระบบแล้ว" เอง —
  **พิสูจน์ด้วย replay planner จริงกับข้อมูล prod** ไม่ใช่อ่านโค้ดแล้วเชื่อ
- ขาเงินเบิ้ลไม่ได้อยู่แล้ว: 2 เลขวิ่งชนงานแถวเดียว → duplicateFid guard (ใบเดียว) +
  settlement double-pay guard (คนละใบ)

## 4. ทางเข้าหลอก (dead entry) — ตัดของตายให้ขาดด้วยข้อมูล ไม่ใช่ความจำ

owner งงลิงก์ CargoCenter บนหน้าอี้อู ("ใช่ของเราหรอ ยังใช้อยู่ไหม") — คำตอบที่ถูกคือ
**นับงานจริง**: `SELECT fwarehousename, count(*)` → MOMO 961 · TTW 32 · **ที่เหลือ 0 ทุกตัว**
→ ตัดเป็น redirect (ไม่ลบไฟล์ · บุ๊กมาร์กเก่าไม่ 404). เมนู/แถบ tab ที่ลิงก์ไปหน้า 0 งาน
= ทางเข้าหลอกที่ทำให้ "แต่ละหน้าเหมือนคนละเว็บไซต์". นำทางของ workflow เดียวกันต้องเป็น
**component เดียว** (`components/admin/warehouse-workspace-nav.tsx`: breadcrumb + แท็บ
โกดัง + เครื่องมือของโกดังนั้น + ↩ ทางกลับ) — ไม่ใช่แต่ละหน้าประดิษฐ์แถบของตัวเอง.
