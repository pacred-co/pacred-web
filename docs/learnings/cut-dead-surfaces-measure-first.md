## 2) หน้าที่ "โชว์ 0 ตลอดกาล" อันตรายกว่าหน้าที่ไม่มี — §0e ตัวจริง

กรอบ "เอกสารของออเดอร์ (0)" ดูเหมือนแค่ยังไม่มีข้อมูล แต่จริงๆ **โครงสร้างทำให้ไม่มีวันมีข้อมูล**:
- ฝั่งฝากสั่งซื้อ: อ่าน `tb_shop_tax_invoice` (prod 0 แถว) แล้วดึงใบเสร็จผ่าน `receipt_id`
  ของใบกำกับนั้น ⇒ **ไม่มีใบกำกับ = ไม่มีทางโชว์ใบเสร็จ** ทั้งที่ `tb_receipt` มี 261 ใบจริง
- ฝั่งฝากนำเข้า: `return { taxInvoices: [], receipts: [], customs }` — **เขียนว่างตายตัว**

**กติกา:** เจอกรอบที่โชว์ 0 → อย่าเดาว่า "ยังไม่มีข้อมูล" ให้ไล่ว่ามันอ่านตารางไหน
แล้วเทียบกับตารางที่ข้อมูลจริงอยู่. ถ้าคนละตัว = กรอบหลอก ต้องซ่อมหรือตัด ห้ามปล่อย.

## 3) `tsc` ไม่จับลิงก์ตาย — ต้องไล่ด้วย grep เสมอ

ลบ 79 ไฟล์แล้ว **tsc = 0** ทันที เพราะ `href="/admin/freight/..."` เป็น **string**
ไม่ใช่ import. ที่ต้องไล่เองหลังลบหน้า:

- `sidebar-menu.ts` (leaf const + ที่ใช้ในเมนู) · `accounting-menubar.ts` · badge map
- `phase-access.ts` · `service-dashboard.ts` `drillHref` · `workspace.ts` คิวงาน
- `work-item.ts` deep-link · การแจ้งเตือน (`link_href` / `url`) ← **ตัวนี้ลืมง่ายสุด**
  (พนักงานกดจากกระดิ่งแล้วเจอ 404 หลังจากนั้นเป็นเดือน)
- ปุ่มบนหน้า**อื่น**ที่พาเข้ามา (เช่นปุ่มบนหน้าคาร์โก้ที่พาไปหน้าใบขน)

`grep -rn '<prefix ที่ลบ>' app/ lib/ components/ actions/` แล้วแยกคอมเมนต์ออกจากโค้ดจริง.
ลิงก์ที่พังต้องชี้ไปหน้าที่**เปิดได้จริง** (เช่น `/admin/board`) ไม่ใช่ปล่อย 404.

## 5) regex ตัด JSX = อันตราย ให้ตัดด้วย "หาบรรทัดเปิด-ปิด" แทน

รอบนี้ regex กิน JSX เกินไป 3 ครั้ง (PageHeader ที่มี `subtitle={<>…</>}` ทำให้ `/>`
แมตช์เร็วเกินไป · `<div>` ครอบถูกกินไปด้วย). วิธีที่ปลอดภัย:

```python
i  = บรรทัดที่มี component
st = ไล่ขึ้นจนเจอ '{/*'          # เปิดคอมเมนต์
en = ไล่ลงจนเจอ '</div>' / '/>'  # ปิดของจริง
del L[st:en+1]
```
แล้ว `tsc` ทันทีทุกครั้ง — เจอพังรู้ทันทีว่าตัวไหน ไม่สะสม.

## 6) "รวม DB เป็นที่เดียว" ≠ "ทุกจอถามที่เดียวกัน"

owner ถาม: *"ทำไมมีมอบหมายมาหมดทุกคนทุก row · ยังไม่ได้รวมตาราง DB เป็นก้อนเดียวอีกหรอ"*

ความจริง: **ข้อมูลพนักงานรวมเป็นตารางเดียวแล้วจริง** (`tb_admin` · mig 0292) —
แต่ dropdown เรียก `listActiveAdmins()` = active ทุกคน (22) เพราะ **ไม่เคยอ่านผังองค์กรเลย**.

**คนละแกนกัน — ต้องถามให้ถูกแกน:**
- `tb_admin` = **ตัวตน** (ชื่อ · เบอร์ · รูป · สถานะ)
- `hr_org_units` + `org_unit_id` = **ตำแหน่ง / ใครทำงานอะไรได้**

⇒ ตัวเลือก "ใครทำงานนี้ได้" ต้องกรองด้วย**ผัง** ไม่ใช่ list-all-then-hope.
ทำ `listAdminsByOrgUnitNames(names)` เป็นตัวกลาง → เปลี่ยนคนที่ผัง
`/admin/hr/org-chart` แล้วทุก dropdown เปลี่ยนตามทันที **ไม่ต้องแก้โค้ด**.
fail-soft: ผังยังไม่จัดคน (ลิสต์ว่าง) → ปล่อยเลือกได้ทั้งหมดไปก่อน ไม่ล็อกจนทำงานไม่ได้.

## 7) uid ดิบบนจอ = บั๊กในสายตาคนใช้ แม้ระบบจะถูก

`IPC : 54adf629-d0fb-442f-…` ทำให้ owner คิดว่าบั๊ก + ถามว่า *"ต่างกับคอลัมน์ผู้สั่งซื้อตรงไหน"* —
ทั้งที่มันคนละคนจริง (IPC = คนเปิดออเดอร์ให้ · ผู้สั่งซื้อ = คนไปกดสั่งของจีน).

**2 กติกา:** (ก) ห้ามให้ uid/รหัสภายในโผล่บนจอ → resolve เป็นชื่อเล่นด้วย SOT ตัวเดียว
(`resolveStaffNameMap`) เสมอ · (ข) ป้ายต้องเขียนเป็นภาษาคนที่บอกความหมาย
(`เปิดออเดอร์โดย: มะนาว` ไม่ใช่ `IPC : <uid>`) — ไม่งั้น 2 คอลัมน์ที่คนละความหมาย
จะดูเหมือนซ้ำกัน. เดียวกับ `PRF เหมาๆ (PCSF)`: **โค้ดที่เก็บใน DB ห้ามแตะ แต่บนจอ
ต้องเห็นแค่ชื่อแบรนด์**.
