# จอคิดสูตรนึง ตัวเก็บเงินคิดอีกสูตร = เก็บเงินขาดเงียบ (2026-07-27)

**เคส:** owner ทัก *"เจ้าหน้าที่ทำราคามา 151k ทำไมลูกค้าเห็นแค่ 150k ลูกค้าจะจ่ายตังแล้ว"*
(P22456 · PR075). ส่วนต่าง **฿618 = ค่าลังไม้ ¥120 × เรท 5.15 เป๊ะ** — ไม่ใช่การปัดเศษ.

## ราก

ยอดขายฝากสั่งซื้อถูกคิด **2 ที่ ด้วยสูตรคนละแบบ**:

| ที่คิด | สูตร | เลข |
|---|---|---|
| จอแอดมิน / ใบเสนอราคา (ภูม 2026-07-01) | (สินค้า + ขนส่งจีน + **ลังไม้**) × เรท + ค่าบริการ | 151,219.45 |
| `htotalpriceuser` ที่เก็บลง DB (writer ทุกตัว) | (สินค้า + ขนส่งจีน) × เรท + ค่าบริการ | 150,601.45 |

ตัวที่เก็บเงินจริง (modal ลูกค้า · บิล · ใบเสร็จ) อ่านค่าที่ **เก็บไว้** → ลูกค้าเห็นยอดต่ำกว่า
ที่ Pricing เสนอไปทุกออเดอร์ที่ตีลังไม้.

ที่ทำให้ไม่มีใครจับได้เร็ว: action เซฟค่าลังไม้ (`adminUpdateOrderCrate`) **เขียนคอมเมนต์ยืนยันไว้เลย**
ว่า "ค่าลังไม้ไม่ใช่ส่วนหนึ่งของยอดขาย" — คอมเมนต์เก่าที่ขัดกับจอที่เปลี่ยนไปแล้ว
กลายเป็นหลักฐานปลอมที่คนอ่านโค้ดเชื่อ.

## บทเรียน

1. **ยอดเงินหนึ่งก้อน = สูตรเดียว ที่เดียว.** พอ "จอ" กับ "ตัวเก็บ" คิดเอง คนละที่
   แล้วมีใครแก้ข้างเดียว → drift ทันที และเงียบ (ไม่มี type checker จับ ไม่มีเทสจับ).
   FIX = SOT ฟังก์ชันเดียว (`lib/shop-order/sell-total.ts`) แล้วบังคับทุก writer เรียกตัวนั้น.
2. **ตามหา writer ให้ครบก่อนประกาศว่าแก้แล้ว.** ยอดนี้ถูกเขียนจาก **5 ทาง**
   (ตั้งราคา · แก้เรท · แก้ค่าลัง · ลบรายการ · refund) — แก้ 4 = ยังพังจากทางที่ 5.
   วิธี: `grep -rn "htotalpriceuser" actions/` แล้วไล่ทีละตัว ไม่ใช่แก้เฉพาะทางที่เจอเคส.
3. **คอมเมนต์ที่ยืนยันกติกาเงิน = ต้อง verify กับจอ ไม่ใช่เชื่อ.** คอมเมนต์ไม่ถูก
   compile และไม่ถูกเทส — มันเก่าได้เงียบๆ เหมือนโค้ด แต่หลอกคนได้มากกว่า.
4. **ปัดเศษ: ใช้ helper กลางเสมอ.** เขียน `Math.ceil((n + EPSILON) * 100) / 100` เอง
   ให้ผลผิดจริง (29,363 × 5.15 → 151,219.46 แทน .45) เพราะ epsilon คงที่ไม่พอกับเลขใหญ่ ·
   ตัวกลาง `roundUp` สเกล epsilon ตามขนาดตัวเลข.
5. **data-fix: แก้เฉพาะที่ยังไม่จ่าย.** ออเดอร์ที่จ่ายแล้วเงิน freeze — เก็บเพิ่มต้องใช้
   flow เก็บเพิ่ม + owner เคาะ ห้ามสคริปต์ไปขยับยอดบนเอกสารที่ออกไปแล้ว.
