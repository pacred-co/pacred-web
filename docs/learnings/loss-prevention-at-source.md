# กันงานขาดทุน — ต้องปิดที่ "ต้นทาง" และต้องพิสูจน์ด้วยข้อมูลว่าปิดจริง

**2026-07-30** · owner: *"ขาดทุนที่เก็บตังแล้ว ต้องยอมแหละครับ และต้องเอามาออกเป็นรายงาน
อย่างละเอียดเป็น report ทั้งหมดครับ และ ต่อไปจากนี้ ห้ามมีงานขาดทุนอีกแล้วนะครับ"*

ก่อนหน้านั้น owner ตีกลับข้อเสนอของผมด้วยประโยคที่เป็นแก่นของบทเรียนนี้:

> *"เงินหายตอนคิดจริงเป็นบัคที่ต้องแก้ไหมครับ **ไม่ใช่มาทำด่านอะไรแบบนี้นะครับ ด่านสอง**หนะครับ"*

---

## 1. "ด่านเตือน" ≠ "แก้บั๊ก" — owner แยกออก และแยกถูก

ผมเจองานขายต่ำกว่าทุน 37 แถว แล้วเสนอจะทำ **ด่านเตือนตอนวางบิล** ว่า "แถวนี้ขายต่ำกว่าทุน".
owner ปฏิเสธทันที เพราะ:

- ด่านนั้นอยู่ **ปลายทาง** — กว่าจะเตือน ราคาถูกตั้งไปแล้ว ลูกค้ารับรู้ยอดแล้ว
- มันรักษา**อาการ** ไม่ใช่**โรค** — ทุกครั้งที่เตือนคือระบบยอมให้เกิดขึ้นแล้วครั้งหนึ่ง
- ด่านซ้อนด่านทำให้พนักงานชิน แล้วกด "ผ่าน" โดยไม่อ่าน

**กติกา:** เจอเงินผิด → ถามก่อนว่า *"ค่านี้ถูกเขียนลงไปตอนไหน"* แล้วไปปิดตรงจุดนั้น.
ด่านที่ยอมรับได้ = ด่านที่อยู่ **ตรงจุดที่ค่าถูกเขียน** (ตั้งเรท / ออกใบเสนอราคา) ไม่ใช่
ด่านที่มาอ่านค่าที่เขียนไปแล้ว.

---

## 2. อย่าเชื่อว่า "ยังพัง" — วัดก่อน บางทีมันปิดไปแล้ว

ผมกำลังจะสร้างกลไกกันขาดทุนใหม่ทั้งชุด. พอเอาข้อมูลจริงมาแยกรายสัปดาห์:

| สัปดาห์ | งานที่มีทั้งราคา+ทุน | ขาดทุน |
|---|---:|---:|
| 07-06 มิ.ย. | 69 | 11 |
| 22-28 มิ.ย. | 112 | 5 |
| 12-18 ก.ค. | 144 | 2 |
| 19-25 ก.ค. | 376 | 2 |
| **26 ก.ค.+** | **74** | **0** |

**แถวขาดทุนล่าสุดทั้งระบบ = 20 ก.ค.** · หลัง 21/07 ตั้งราคา **287 แถว ขาดทุน 0**

ตัวที่ปิดคลาสนี้คือคำสั่ง owner เอง 21/07 — **`CHARGE_HIGHER_BASIS`** ("เก็บค่าที่แพงกว่า")
เพราะขาดทุนเกือบทั้งหมด **ไม่ได้มาจากเรทคิวต่ำ แต่มาจากเรทกิโล** (฿17/12/8/20 ต่อ กก.)
บนตู้ที่ทุนคิดเป็นคิว — พัสดุเบาแต่ใหญ่ = เก็บได้น้อยกว่าทุนเสมอ. พอบังคับให้คิดทั้ง 2 ฐาน
แล้วเก็บฐานที่แพงกว่า ช่องนั้นก็ปิดไปเอง.

**ถ้าไม่วัด ผมจะสร้างกลไกซ้ำกับของที่ทำงานอยู่แล้ว** (ซ้ำรอย L-AUD "verify ก่อน build").

### วิธีพิสูจน์ที่เชื่อได้ = พิสูจน์ "เชิงบวก" ไม่ใช่แค่ "ไม่มีเคสใหม่"
"เดือนนี้ไม่มีเคส" อาจแปลว่า *ไม่มีงาน* ก็ได้ → ต้องแสดง **ตัวหาร**:
*"ก.ค. มีงานเข้าเงื่อนไขเดียวกัน 287 แถว และถูกทุกแถว"* ถึงจะเป็นหลักฐาน.
(ใช้ท่าเดียวกันกับบั๊ก famountcount: มิ.ย. 70 แถว/ผิด 9 → ก.ค. 193 แถว/ผิด 0)

## 3. ข้อยกเว้น "grandfather" = ระเบิดเวลาที่ไม่มีวันหมดอายุ

ด่านพื้นราคาใน `adminSaveCustomerRate` (19/06) บล็อกเฉพาะ**เซลที่เพิ่งตั้งใหม่** และ
**ยกเว้นเซลเก่าที่ไม่ได้แก้** — เหตุผลตอนนั้นถูก (เซฟเรื่องอื่นของลูกค้าเก่าต้องไม่พัง = กันงานหาย).

แต่ข้อยกเว้นนั้น **ไม่ได้แยกระดับความรุนแรง** จึงครอบไปถึงเซลที่ต่ำกว่า **ทุนจริง** ด้วย
⇒ เซลนั้นอยู่ในตารางได้ตลอดกาล และออเดอร์ถัดไปของลูกค้ารายนั้น **ขาดทุนแน่นอน
ตั้งแต่วินาทีที่คิดราคา** (prod: 12 เซล / 5 ลูกค้า · โชคดีที่ทั้ง 5 ยังไม่เคยมีงาน).

**กติกา:** ข้อยกเว้นแบบ grandfather ต้อง**แบ่งชั้นตามความเสียหาย**เสมอ —
- ผิดนโยบายแต่ยังไม่เสียหาย → ยกเว้นได้
- **เสียหายแน่นอน** → ห้ามยกเว้น (บล็อกแม้ผู้ใช้ไม่ได้แตะเซลนั้น)

ผลข้างเคียงที่ดี: เซลพิษ**ออกจากระบบไม่ได้เงียบๆ** — ครั้งต่อไปที่ใครเปิดเรทลูกค้ารายนั้น
จะถูกบังคับให้แก้ โดย**ไม่ต้องไปไล่แก้ราคาใครเงียบๆ ล่วงหน้า** (ซึ่งเป็นการเปลี่ยนเงินของ
ลูกค้าโดยไม่มีใครสั่ง).

## 4. พื้นกันขาดทุน ต้องอ่านทุนจาก "ตัวเดียวกับที่คิดต้นทุน"

`sell-cost-floor-core.ts` อ่าน `tb_settings.fcost{car|ship}{1..4}defaultmomo[2]` —
**คอลัมน์ชุดเดียวกับ `resolve-cost.ts`** ที่คิดต้นทุนจริง.

ถ้า hardcode ตัวเลข 4,700/2,500 ไว้ วันที่บัญชีขยับทุนที่ `/admin/settings` พื้นจะค้าง
= กันขาดทุนไม่ได้เงียบๆ. **เลขเดียวกันห้ามมี 2 แหล่ง** (ซ้ำรอย
[`display-vs-stored-money-formula.md`](display-vs-stored-money-formula.md)).

รายละเอียดที่ต้องคิดเผื่อ: ใช้ **ค่าต่ำสุด**ของ 4 ประเภทสินค้าเป็นพื้น (ไม่บล็อกเกินจำเป็น) ·
อ่านไม่ได้ → ค่าสำรอง (ยังบล็อกได้ ไม่ปล่อยผ่านหมด) · เรท 0 = ไม่ได้ตั้ง ไม่ใช่ขาดทุน
(ลูกค้าที่คิดตามกิโลอย่างเดียวต้องเซฟได้) · เท่าทุนพอดี = ไม่บล็อก (กำไร 0 เป็นดุลพินิจ owner).

## 5. รายงานเงินย้อนหลัง ต้องแยก "ขาดทุนจริง" ออกจาก "ติดลบรายกล่อง"

นับดิบรายกล่องได้ **−฿11,094** แต่ความเสียหายจริงคือ **−฿3,113.58**.
ส่วนต่างคือ 12 ชิปเม้นที่กล่องหนึ่งติดลบแต่พี่น้องในชิปเม้นเดียวกันชดเชยจน **กำไร +฿33,371**
(ขายคิดตามน้ำหนัก · ทุนคิดตามคิว → กล่องเบาใหญ่ติดลบรายตัวเป็นเรื่องปกติ).

**รายงานเงินต้องรวมกลุ่มก่อนสรุป** ไม่งั้นเลขเว่อร์ 3.5 เท่า และคนอ่านจะตัดสินใจผิด
(เช่นสั่งขึ้นราคาลูกค้าที่จริงๆ แล้วทำกำไรให้อยู่).

## 7. "ปิดที่ต้นทาง" ต้องนับให้ครบว่าต้นทางมีกี่ทาง

owner สรุปโมเดลราคาให้เองว่า: *"ไม่อิงเรทใบเสนอราคา ถ้าไม่ได้ออก ก็อิงเรทราคากลาง
ไม่งั้นก็ต้องติ๊ก ใส่ราคาขายเอง **มีแค่นั้นครับ**"* — ประโยคนี้คือ spec ที่ใช้ตรวจได้:
ราคาขายถูกเขียนได้จาก **3 ทางเท่านั้น** และตอนแรกผมปิดไปแค่ทางเดียว

| ทางที่เขียนราคาขาย | ก่อนหน้า | หลังแก้ |
|---|---|---|
| เรทกลาง `tb_rate_g_cbm` (ลูกค้าส่วนใหญ่) | ❌ ไม่มีพื้นเลย | ✅ บล็อก |
| เรทเฉพาะตัว `tb_rate_custom_cbm` | 🟡 มีพื้น แต่ยกเว้นเซลเก่า | ✅ ต่ำกว่าทุน = บล็อกเสมอ |
| เรทกำหนดเองรายงาน `customratecbm` | ❌ รับ 0–99,999 | ✅ บล็อก (ข้ามงานที่จ่ายแล้ว) |

ที่พลาดง่ายสุดคือ **เรทกลาง** — เพราะ "มีพื้นอยู่แล้ว" เป็นความจำผิด (พื้นอยู่ที่เรท
*เฉพาะตัว* คนละไฟล์กัน) และมันคือช่องที่**รุนแรงที่สุด**: ตั้งผิดทีเดียว ลูกค้าทุกคนที่
ไม่มีเรทเฉพาะตัวขาดทุนพร้อมกัน. **grep ทุก write path ของค่าเดียวกัน อย่าเชื่อว่าปิดแล้ว
เพราะเห็นด่านอยู่ที่ไฟล์หนึ่ง.**

## 8. ก่อนติดด่าน ต้องวัด "รัศมีผลกระทบ" กับ prod เสมอ

ด่านเรทกำหนดเองรายงาน ตอนเขียนเสร็จผมวัดก่อน apply: prod มี **296 แถวเปิด override**
→ เข้าข่ายต่ำกว่าทุน **8 แถว** → **ทั้ง 8 เป็น `fstatus=7` ส่งสำเร็จไปแล้ว**.

ถ้าไม่วัด ด่านจะบล็อกการเซฟงานที่ปิดไปแล้ว (พนักงานแก้โน้ต/ที่อยู่ไม่ได้ เพราะราคาที่
เก็บเงินไปแล้วเมื่อเดือนก่อน) = งานหาย. เติมเงื่อนไข `fstatus < 6` → **รัศมี = 0 แถว**.

**กติกา:** ด่านใหม่ทุกตัว ต้องตอบให้ได้ว่า *"วันนี้มันจะบล็อกใครบ้าง"* ด้วยเลขจาก prod
ก่อน ship — ไม่ใช่หลัง.

## 9. ล้างบัญชีผี — ใช้ "เกณฑ์" ไม่ใช่ "ชื่อที่ดูเหมือน"

owner: *"ลบคลีนไปเลยก็ได้ครับ เอาที่เป็นผีๆ พิเศษนะครับ ไม่ใช่ลบ user ทั่วไปออกไปด้วย"*

ผมเกือบเสนอลบจาก**ชื่อที่ดูเหมือนบัญชีทดสอบ** (FCL · PW · JET · "PCS CARGO") พอเปลี่ยน
เป็นสแกนด้วย**เกณฑ์** (รหัสไม่ใช่ `PR<ตัวเลข>` + 0 ความเคลื่อนไหวทุกตาราง + ไม่ใช่พนักงาน)
เจอ 11 บัญชี และในนั้นมี **2 ตัวที่ห้ามแตะเด็ดขาด**:
- `AD001` = **วิสิฐ ศิลปเลิศลักษณ์ = พี่ป๊อป เจ้าของกิจการเอง**
- `AD006` = บัญชีทดสอบ UI ของ**ปอน** ที่มีงานจริง 7 รายการ + ใบเสร็จ 2

ถ้าเดินตาม "ชื่อที่ดูเหมือน" อย่างเดียวก็ยังรอด แต่ถ้าเผลอเหมารหัสแปลก = ลบบัญชีเจ้าของ
กิจการ. **สแกนด้วยเกณฑ์ + ใส่ NEVER-list ในสคริปต์ + re-verify ทุกเกณฑ์ตอนรันจริง**
(ไม่ใช่เชื่อลิสต์ที่ hardcode ไว้).

**soft-delete ไม่ hard-DELETE:** ตารางบ้านเรา**ไม่มี FK** (§0e) — ลบแถว `tb_users` จริง
แล้วอาจมีที่อื่นชี้ค้างเงียบๆ และกู้ไม่ได้. ใช้ `userStatus='0'` + `profiles.is_active=false`
(คอนเวนชันเดิมที่ signup-dedup เช็คอยู่แล้ว) = หายจากทุกลิสต์ แต่ย้อนกลับได้ ·
แล้ว**ลบเฉพาะเรทเฉพาะตัวทิ้งจริง** เพราะนั่นคือตัวเสี่ยงเงิน (144 เซล · ในนั้นต่ำกว่าทุน 10).
