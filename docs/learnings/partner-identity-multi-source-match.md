# คู่ค้าส่ง "เลขเดียวกัน" มาหลายชนิด — จับคู่ด้วยยอด ไม่ใช่ด้วยเลข

> 2026-07-29 · เคส MOMO "สรุปพัสดุนี้อยู่ตู้ไหนกันแน่" · owner บ่นว่าเลขตู้ไม่ตรง งงไปหมด

## บทเรียนหลัก

**คู่ค้าส่งฟิลด์ที่ "ชื่อเหมือนเลขตู้" มาให้เรา 3 ชนิด และมีชนิดเดียวที่เป็นเลขตู้จริง.**
ถ้าอ่านชื่อคอลัมน์แล้วเชื่อ จะประทับเลขผิดลง DB แบบเงียบๆ:

| ฟิลด์ | หน้าตา | จริงๆ คืออะไร |
|---|---|---|
| `momo_container_no` | `PR20260708-SEA01` | **รอบขนส่ง** (วันที่+โหมด+ลำดับ) |
| `container_batch_no` | `GZS260710-1` | เลขตู้จริง — แต่ **null เกือบหมด** |
| ไฟล์แพคกิ้งลิสต่อตู้ | `GZS260710-1` | เลขตู้จริง **+ ยอดต่อพัสดุต่อตู้** ← ความจริง |

**วิธีจับคู่ที่ใช้ได้: เอา "ยอด" มาจับ ไม่ใช่ "เลข".** จัดกลุ่มแถวย่อยตามฟิลด์ที่คู่ค้าจัดกลุ่มไว้แล้ว
(รอบขนส่ง — เชื่อได้แม้ไม่ใช่เลขตู้) แล้วเทียบยอดของกลุ่มกับยอดในไฟล์ (จำนวนแถว · Σ น้ำหนัก · Σ คิว).
ตรงระดับทศนิยม = ชี้ตัวเดียวได้แบบไม่ต้องเดา — prod 6 ชิปเม้น 15 กลุ่ม ตรง 100%.

เลขที่ *ดูเหมือน* กุญแจแต่ใช้ไม่ได้: **CG range** (`CG83584631177-CG83584631217`) — ช่วงของแถวย่อย
คาบเกี่ยวกันเอง (`-8` = 631217-631230 · `-9` = 631223-631235) → จับผิดตัวแน่. เก็บอ้างอิงได้ ห้ามตัดสิน.

## กติกาที่ตกผลึก

1. **ห้ามเดาเมื่อจับคู่ไม่ลงตัว.** จับได้หลายตัว/ไม่ได้เลย → คืนเหตุผลให้คนตัดสิน ไม่ประทับค่า.
   เลขตู้ผิด = ฐานคิดต้นทุนผิด = เงินผิดเงียบ. `ambiguous` / `unmatched` / `no_packing`
   เป็นผลลัพธ์ที่ถูกต้อง ไม่ใช่ความล้มเหลว.
2. **ตัวเลือกเดียว = ไม่ต้องเทียบ.** ถ้าไฟล์บอกว่าของอยู่ตู้เดียว ก็จบ — ไม่ต้องเอายอดมาเสี่ยง
   false-negative จากการปัดเศษ.
3. **tolerance ต้องมี แต่ต้องเล็ก.** คู่ค้าปัดเศษระหว่าง "ไฟล์" กับ "API" ไม่เหมือนกัน
   (±0.6 kg · ±0.02 คิว พอ) — ถ้าต้องผ่อนเกินนี้ แปลว่ากำลังจับคู่ผิดฐาน.
4. **1 ชิปเม้น = N ตู้ ได้จริง** (ของไม่พอตู้ / ปิดตู้ทัน). อย่าเขียนโค้ดที่สมมติว่า
   ครอบครัวหนึ่ง = ตู้หนึ่ง — และเมื่อแก้ข้อมูลแล้ว ต้องกัน **ทางเขียนเดิม** ไม่ให้ประทับ
   ค่าจากหัวไฟล์ทับกลับ (re-poison) ไม่งั้นแก้แล้วเด้งกลับทุกครั้งที่มีคนกด apply.
5. **ต้องมีที่เดียวที่ตอบว่า "อันไหนถูก".** เดิมทั้ง 2 หน้าคำนวณ "ไม่ตรง" ของตัวเอง
   (`cabDiff` ฝั่งแพคกิ้ง · `cabinetConflict` ฝั่งใบวางบิล) แล้ว **ไม่มีหน้าไหนตอบได้ว่าตู้ไหนถูก**
   → ผู้ใช้เห็นแค่ "ไม่ตรง" แล้วตัน. เขียน SOT ตัวเดียวที่ตอบ + ให้ทุกหน้าเรียกตัวนั้น.
6. **การพิสูจน์ว่าเงินไม่ขยับ ต้องคำนวณ ไม่ใช่สมมติ.** สคริปต์แก้ข้อมูลคิดเรทของ *ทั้งค่าเดิมและ
   ค่าใหม่* แล้วบังคับให้เท่ากันเป๊ะจึงเขียน — ต่างแม้บาทเดียว = ข้าม+flag. เขียน comment ว่า
   "ตระกูลเดียวกันเรทเท่ากัน" แล้วเขียนเลย = ความเสี่ยงที่ตรวจไม่ได้.
7. **fixture ต้องมาจาก prod.** เทสใช้ 3 ชิปเม้นจริงพร้อมตัวเลขจริง — ถ้ากุตัวเลขเอง
   กฎจับคู่จะ "ผ่าน" ทั้งที่ tolerance/ลำดับความเชื่อผิด (บทเรียน 2026-07-17 ซ้ำรอย).

## สัญญาณว่ากำลังเจอคลาสนี้

- ผู้ใช้พูดว่า "เลข… ไม่ตรง แปลกๆ" + "สรุปมันอยู่ที่ไหนกันแน่" → มีหลายแหล่งที่อ้างเลขเดียวกัน
- มีตารางที่ **มีคอลัมน์เลขจริงแต่เป็น null เกือบหมด** ข้างๆ คอลัมน์ที่มีค่าครบแต่ไม่ใช่เลขจริง
- โค้ดคำนวณ flag "ไม่ตรง" ไว้แล้วแต่ **ไม่มีใครอ่าน** (grep เจอ 0 hits ใน UI) = อาการที่บอกว่า
  คนเขียนรู้ว่ามีปัญหาแต่ตอบไม่ได้ว่าอันไหนถูก จึงไม่กล้าแสดง
